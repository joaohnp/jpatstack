# Review

For “is this right?” or “show me the proof,” check that claim directly. Run the command, drive the screen, or read the actual value. Compare equivalent inputs. For a number, check the underlying records against the rule; a second display isn't independent evidence. A local run doesn't establish what's live; an after-only run doesn't establish improvement. No full review is needed.

For a change review, recover the intent from the request, issue, or agreed example. Inspect the diff and the other paths that compute or consume the changed rule. For a CPA card and report, use the same filters, period, and population. Then work out the expected value from the underlying records. Two views that share a wrong denominator will agree. Two views with different definitions can legitimately differ.

Try to disprove each finding. For a behavioral blocker, give the case or command, the result you saw, and what the requirement says should happen. Distinguish a regression from an existing discrepancy. For maintainability, ask “where does this value come from?” and “what can change it?” A needless wrapper or a repo convention violation may matter; label it as such, not as a runtime failure.

**Winning condition:** Lead with the verdict and the evidence that decides it. Show the blocker, say “no blockers found” in the checked scope, or name the material fact still unverified. For a proof request, stop once the claim is settled. Don't apply fixes.
