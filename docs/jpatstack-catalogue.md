# jpatstack — proposed skill catalogue

## How to use it

Speak normally. “Why does this menu disappear?”, “let me try it locally”, and “show me the proof” are requests, not commands to memorize. `grill-with-docs` is the one mode worth deliberately invoking for a sustained design conversation. Any mode may ask a spontaneous question when the agent can't settle it from the evidence and the answer would change the work. A question does not turn the session into an interview.

This is a proposed **standalone** collection. Include the selected upstream instructions, examples, and any necessary references inside jpatstack, with attribution and applicable license notices. Upstream links below are provenance, not dependencies. Removing Matt’s installed skills must not break jpatstack.

## Shared defaults

- **First principles:** start with what someone needs to do or decide. Trace one concrete case from inputs to outcome. Separate the facts, the business rule, and the mechanism currently in the code. The current design is evidence, not necessarily the intent.
- **KISS:** of the options that meet the actual requirement, choose the one a colleague can most easily explain and change. Prefer the path the app already uses when it fits. A small diff that leaves two definitions of CPA is not the simpler design.
- **YAGNI:** before adding a layer, flag, field, test, or ticket, name the present behavior, risk, or handoff that needs it. If the only case is “we might want it later,” leave it out. Apply this to agent ceremony as well as code.

These are rules for choosing what to do, not headings the agent must recite. Keep upstream wording when we want upstream behavior. In particular, keep the trigger, the action it requires, and what the person can do with the output. “Give a recommendation” isn't equivalent to “reply `1 yes; 2 no` to a numbered round.” Keep the example, format, or pause that makes the interaction work. If we deliberately change that behavior, say what conflicts with our workflow in the last column below.

**Design is two questions, not two more skills.** Domain: what does this mean to the business? Code: where does that rule already live, and who should own it? For CPA, decide what counts as an acquisition, then find the calculation that both card and report should read. If meaning and ownership are clear, proceed. No separate design document or new module is implied.

**A check is not necessarily a permanent test.** Verify changed behavior. Keep a new automated test only if (1) it catches a named, consequential failure worth catching again, (2) existing coverage would miss it and extending an existing case would not suffice, and (3) it exercises observable behavior with an independent expected result. It should fail for a plausible wrong implementation and survive a behavior-preserving refactor. Prefer a focused before/after check for mock layouts, copy, or one-off investigation. For a high-consequence risk without a reliable check, report the gap rather than treating manual inspection as equivalent. Required repo checks still apply.

**Proof is part of done.** Say what changed for the user, show the observation supporting it, and provide the shortest way to inspect it (local URL, screenshot, command/output, or comparable measurement). Use the same case before and after where possible; if no baseline was captured, say so. A passing build or test count alone doesn't demonstrate a reported glitch is fixed. “Show me the proof” asks for evidence of a particular claim, not more implementation. Use a decision log only when the history of a long run is itself needed.

**Leave ordinary mechanics to the model.** No standing benchmark or PR ritual: adapt to the task. Back a speed claim with comparable measurements, and distinguish verified locally, committed, pushed, and deployed. Stop at the requested handoff.

**ADRs follow Matt’s flow, not a separate command.** When a choice settles, offer an ADR if it is hard to reverse, surprising without context, **and** a real trade-off. Use the next number in `docs/adr/NNNN-slug.md`: a title and 1–3 sentences of context, decision, and why. Add alternatives or consequences only when worth remembering. Link the decision from the spec instead of retelling it there.

**`earn-the-diff` versus `review`:** In the [May cost-per-win example](../skills/earn-the-diff/SKILL.md), `earn-the-diff` checks the calculator against the independently worked R$40. `review` also checks which deals the KPI card and report count: both could include June's win and agree on the same wrong R$30.

**Review the drafts first:** [grill-with-docs](../skills/grill-with-docs/SKILL.md) and [earn-the-diff](../skills/earn-the-diff/SKILL.md) replace the two defaults that cost the most repeated steering: exhausting every design branch and doing more implementation or verification than the request calls for. The [README](../README.md) links all seven drafts.
